## 1. 命名与区分规则（多台如何区分 —— 已定，别改）

**一个代码文件夹 `ralf/`，一份脚本；每台工作站靠「机器名 + 各自配置」区分。**
（与总纲 §1 一致：型号 → 文件夹；具体设备 → 标识，不是每台一个文件夹。）

| 维度 | 用什么区分 |
|---|---|
| Bioengineering 这一类（型号相同、库结构相同） | 一个 `ralf/` 目录 + 一份 `ralf_ingest.py` |
| 每一台具体工作站 | **机器名 = `<Windows 主机名>_Bioengineering`**（一台一个，贯穿 NAS 所有目录，一旦定不改名） |
| 每台的配置/凭据 | `/etc/instrument-ingest/ralf-<机器名>.env` + `ralf-<机器名>.cnf`（各一份） |
| 同一台里的 B8/B9 等罐 | **不额外区分**——只是那台 MySQL 里的不同库，一次 dump 全备进去，dump 内按库名分 |

- 主机名用 `nmblookup -A <ip>` 取（每台各查一次）。**决定用主机名**（负责人 2026-08-04 定）。
- 冷/热库按**名字前缀自动识别**（`db_archive*` = 冷、`pbh*` = 热），不同工作站罐号不同也无需改代码。
- NAS 上每台各成一棵树：`Daily/<机器名>/`、`State/<机器名>_*`、`Checksums/<机器名>/`、`Logs/<机器名>/`。
- 定时器不按台拆：`tools/run-ingest.sh` 里 `ralf` 段**遍历所有 `ralf-*.env`**，一台台跑，前台失败不拖后台。

## 2. 已勘察工作站（实测 2026-08-04，一台）

| 项 | 值 |
|---|---|
| IP | `10.0.13.58`（主机名待 `nmblookup` 取，用于定机器名） |
| 数据库 | **MySQL 4.1.22-community-nt**（2005 年，32 位）；⚠️ 只有 **MariaDB 客户端**能连，MySQL 8 客户端握手不兼容 |
| 端口 | `3306` |
| Windows 服务 | `MySQL`；程序 `C:\Program Files (x86)\MySQL\MySQL Server 4.1\bin\mysqld-nt` |
| 存储引擎 | 归档大表为 **InnoDB**；InnoDB 数据文件 **`D:\MySQL Datafiles\ibdata1`**（autoextend，约 38GB，**是本体不是备份**） |
| 二进制日志 | `log_bin` = **OFF**（无时间点恢复能力） |
| 上层应用 | Bioengineering **RALF** 补料分批发酵系统（配置头 `W30679 RALF+ Engineered Fed-Batch`），B8/B9 两台罐 |

**库结构（每台工作站同构，实测这台）：**

| 类 | 库 | 关键表 | 量级 |
|---|---|---|---|
| **热（实时）** | `pbh` / `pbh_b8` / `pbh_b9` | `t_writevalues`(设定值/写入值)、`t_readvalues`(当前值,无时间戳)、`t_attrvalues`(位号字典 350) | 小 |
| **冷（归档）** | `db_archive_b8` / `db_archive_b9` | **`t_analyze`**(`sUsDateTime`+`iNr`+`dValue`)、`t_batch`(批次清单)、`t_audittrail` | **`t_analyze` ~8900万(b8)/1.05亿(b9)行，各库 ~7–8GB** |

- **三个实时库（`pbh` 无后缀 + `pbh_b8` + `pbh_b9`）都是 ProfiBus Handler 的实时工作库，同构。** 存的是**实时/配置数据，不是持久历史**：
  - `t_writevalues`（实测 2026-08-05 三库均 216 行，且内容相同）= **下发给控制器的设定值/控制参数**：温度设定 `A8_TIC602_SP=37`、搅拌设定 `SIC_SP`、控制模式、PID(`W_PB/W_TI/W_TD`)、灭菌温度/时间(`W_SterTemp/W_SterTime`)、级联上下限等。
  - `t_readvalues`(当前值)、`t_attrvalues`(位号字典 350) **只有"当前加载的那台罐"有数据**（2026-08-05 是 `pbh_b9`：读数 165 / 字典 350；`pbh_b8` 与 `pbh` 当时为 0）。同一时刻通常只一台罐的实时视图被加载，会轮换（2026-08-04 是 b8 有）。
  - ⚠️ `pbh`（无后缀）不是"未启用的空模板"——它装着同样的 216 行设定值。之前误判为"几乎空/模板"，已更正。
  - ⚠️ 行数以**精确 `COUNT(*)`** 为准；`SHOW TABLE STATUS` 对 InnoDB 给的是**估算值**（曾误显示 433/164，实为稳定 216），别拿它当真。
- 实时库存最近约 12 个月（`Generic_Extractor` 每月凌晨 3 点把超过 12 个月的搬进归档并从实时删除）。
  ⚠️ **归档是「迟到数据」**：新进归档的行是 ~12 个月前的老时间戳 → 增量以 `t_batch` 新批次为准，别按测量时间戳取 max。
- 勘察时无批次运行，实时库近乎为空 → **有批次运行时需再确认实时库结构与量**（待办）。

**只读账号（2026-08-04 建）**：`etl_reader` / 见桌面接入记录，`SELECT` on `pbh*` + `db_archive*` 六库。
用直接改 `mysql.db`/`mysql.user`（skip-grant 模式，GRANT 被禁）方式建；**未动 root、未动应用账号 `user`**。

**备份现状**：工作站上**无任何数据库导出备份**；唯一是**群晖 Active Backup for Business 整盘镜像**（代理已装，需去 NAS 确认在跑、覆盖 C+D 盘）。Windows 自带备份未配置。

## 3. 采集策略与「与文件型仪器规范的差异」（重点，flag 给负责人）

ralf 是数据库型源，`INGEST-STANDARD.md` 里为**文件型仪器**写的几条规范套不上，用等价方式替代——**核心铁律不变**（只读、SHA 校验、append-only、凭据不入库、告警+心跳、变更控制）：

| 文件型规范 | ralf 的做法（差异） |
|---|---|
| §4 CIFS `ro` 挂载 | **不挂载**，走 TCP 3306；「只读边界」由**只读 MySQL 账号**保证（绝不用 root / 写账号 `user`） |
| §5 数据源分类 A/B/C/D | 不适用。定义为「**整库逻辑快照**」：冷库月度全量 `mysqldump`、热库周度全量 |
| §6 SHA-256 双向校验 | **照做**，但对象是 **`.sql.gz` 产物**：本地导出算 h1 → 送 NAS → 回读算 h2 → 一致才记账 |
| §7 保留源文件 mtime | 不适用（dump 是现生成的）。改为记录 **dump 生成时刻 + 数据覆盖范围**（行数、`max(t_batch.sStopTime)`）作元数据 |
| §9.1 全设备共用 02:00/11:45/16:00 定时器 | **不共用**。ralf 走**自己的定时器**：热库**每周**、冷库**每月**（安排在抽取器月度任务之后）。理由：cadence 与文件型（每日取新文件）根本不同，无 C 类每晚覆盖的每日紧迫性 |
| §12.1 心跳 dead-man's-switch | **照做**：以「dump 任务有没有按时跑」为健康信号（间隔=每周 168h），不用「业务数据陈旧」（归档月变会误报） |

**mysqldump 要点**：表是 InnoDB → 用 `--single-transaction` **在线一致、不锁库**（只需 SELECT 权限）。
少数 MyISAM/HEAP 表（如 `r_analyze`）不在一致快照内，但体量极小/瞬态，可接受（勘察时确认）。

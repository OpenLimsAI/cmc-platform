## 1. 网络与共享

| 项 | 值 |
|---|---|
| Bridge PC IP | `10.0.13.66` |
| 机器名 | `FLEXIIINTERFACE`（局域网无 WINS/DNS，**名字解析不了，一律用 IP**） |
| 共享 | `\\FLEXIIINTERFACE\Export` |
| SMB 方言 | SMB1 ~ **3.1.1**（用 3.0 即可） |
| 网络路径 | `//10.0.13.66/Export` |

**⚠️ SMB1 仍启用**（`NT LM 0.12 (SMBv1) [dangerous, but default]`）。我方不使用，但属安全隐患，应报 IT 登记。

### 共享权限的实际状态

- **共享权限**：`Everyone` = Full Control / Change / Read **全部允许**
- **但** Windows「密码保护的共享」**开着** → 匿名访问被拒（`NT_STATUS_ACCESS_DENIED`）

即：**一道锁 + 锁后面完全敞开**。只要能认证上任意本地账号，`Everyone` 规则就会放行。

**🚫 不要动共享权限，不要关密码保护：**
- FLEX2 主机很可能**通过网络往 Bridge PC 这个共享写文件**。改 `Everyone` 可能让 Auto Export **当场瘫痪且不报错**
- 关掉密码保护 + `Everyone Full Control` = 整个局域网任何人都能删仪器数据
- **当前唯一的保护就是那道密码锁**

### 账户

| 账户 | 结论 |
|---|---|
| `novaservice` | ❌ Nova 服务工程师账户，**密码每天变**，不可用于自动化 |
| `nova_export_reader` | ✅ 我方新建，普通用户（`C$` 访问被拒 = 非管理员），只读用途 |

**只读如何保证**：共享权限动不得（`Everyone` 会给任何账号 Full Control），
所以**从 Linux 侧锁死** —— 挂载加 `ro`，内核层面不发写请求。脚本启动时再自验一次。

**⚠️ 待办**：Bridge PC 上给 `nova_export_reader` 勾**「密码永不过期」**，
去掉「用户下次登录时须更改密码」。否则 42 天后定时任务静默全挂。

### 验证过的命令

```bash
nc -zv 10.0.13.66 445                                    # succeeded
nmap -p445 --script smb-protocols 10.0.13.66             # 列出 dialects 到 3.1.1
smbclient -L //10.0.13.66 -N                             # ACCESS_DENIED（匿名列清单被禁，正常）
smbclient -L //10.0.13.66 -U nova_export_reader          # ✅ 列出 Export
smbclient //10.0.13.66/C\$ -U nova_export_reader         # ACCESS_DENIED ✅（证明非管理员）
smbclient //10.0.13.66/Export -U nova_export_reader -m SMB3   # ✅
```

## 3. Results/ 里的两套文件

### 关键发现：两种导出的格式**不一样**

| | 逐次导出 | 月度累积 |
|---|---|---|
| 文件名 | `SampleResultsT281240040C2026-07-15_152602.csv` | `SampleResultsT281240040C2026-July.csv` |
| 列数 | **34** | **40** |
| 数据行引号 | **不加** | **全加** |
| 独有列 | — | `Comment`、`Pre-Dilution Multiplier`、`RSM`、**4 个试剂批号列** |
| 是否变化 | 写完不变（immutable） | **整月持续追加** |

### 🔴 列顺序被打乱了

```
逐次： ... pH @ Temp, PCO2 @ Temp, PO2 @ Temp ...
月度： ... pH @ Temp, PO2 @ Temp, PCO2 @ Temp ...      ← 互换

逐次： ... Chemistry Flow Time, pH / Gas Flow Time ...
月度： ... pH / Gas Flow Time, Chemistry Flow Time ...  ← 互换
```

**按列位置解析 = PO2/PCO2 静默调包。** 不报错、数值合理、发现不了。
→ **铁律：按列名映射。**

### 月度独有的试剂批号（GMP 价值所在）

```
"Chemistry Cartridge Lot Number"  26071060
"Chemistry Card Lot Number"       26057032
"Gas Cartridge Lot Number"        26124043
"Gas Card Lot Number"             25339017
```
**逐次文件完全没有这四列。** 试剂批号 → 检测结果的可追溯链，只有月度文件有。
这是"月度 = 主数据源"的决定性理由。

### 逐次文件的来源（已查明）

同事不知道 Auto Export 有效，**每天手动点导出**。已确认 Auto Export 现在是勾着的，
将告知同事停止手动导出。→ **今后只有月度文件。**

逐次文件里重复很多（双击导出）：
```
2026-01-04_150005.csv  129837
2026-01-04_150018.csv  129837   ← 13 秒后，一模一样
```
另有一个残留的 `SampleResultsT281240040C2025-11-25_103557.csv - Shortcut.lnk`（人手工留下的）。
→ 文件名正则须严格锚定 Analyzer ID，避开这类杂物。

### ⚠️ "月度是逐次的严格超集" —— 验证强度不足

对比过**一条**记录（`FBC_SN_D2` / `7/15/2026 8:41:15`），两边**字段完全一致**，
且月度里 `Vessel ID` / `Batch ID` / `Cell Type` 分得清清楚楚（`A6_A6` / `R2601` / `0092`）。

**但样本量是 1，不是 280 个文件、14 个月的证明。**
→ 待办：`--verify-coverage` 做一次性全量核对，通过后才正式弃用逐次文件。

> 补充：7/1 的月度记录里出现过 `Batch ID = "015_R2602_B3_B3"`（三个字段被拼成一串），
> 一度以为是格式问题。对比后确认是**操作员录入习惯**，不是导出行为。属 SOP 问题。

**是配置与状态，不是结果数据**：
- `Sequencing/SequenceManager_DP_ChemCal.xml` —— 化学校准数据（7/14 22:31 更新）

**推测**：`DatabaseBackup.dbb`（14 MB）才是结果数据库本体。

> 大量成员日期为 `2019-04-11` = 出厂镜像默认值。

### 定位

- ❌ 不做数据源：私有格式 + 加密 + 无文档 + 无厂商承诺 + 固件升级可能变 → GMP 环境无法验证

  而 Nova 自己只留一份，不抓就没了

**⚠️ 但必须问 Nova**：一份自己打不开、只能求厂商的备份，

## 8. 全量实测：列错位到底影响什么（2026-07-23，ETL 落库前的复核）

> 背景：立项时的结论（第 3 节）基于**少量样本**。ETL 开工前对 NAS 上
> **15 个月、7704 条数据行**做了全量核对，结论有修正，以本节为准。

### 8.1 🟢 决定性发现：试剂批号没有丢，尾部结构 100% 恒定

短行（未测通道被省略）导致的是**整体左移**，不是尾部字段丢失。
以行宽 `w` 计，下列位置在 **7704/7704 行全部成立**：

| 相对位置 | 字段 | 校验通过率 |
|---|---|---|
| `[0]` | Date & Time | 7704 / 7704 |
| `[w-8] … [w-5]` | **4 个试剂批号列** | 7704 / 7704 |
| `[w-3]` | Sample Time | 7704 / 7704 |

无论行宽是 33 / 35 / 38 / 39 / 41，批号永远在**倒数第 8 到第 5 位**。
→ **试剂批号 → 检测结果的 GMP 可追溯链是完整的，一条没丢。**实测出现过 **75 种批号组合**。

> 少数行 `Gas Cartridge Lot` 为空（如 2026-07 有 20 行）——那是**真的没值**（该通道未使用），
> 不是错位。位置本身仍然对得上。

### 8.2 🔴 修正：错位不是"缺一段"，是**多处分段省略**

原以为短行只是尾部少几列。实测**不是**——省略发生在多个位置。
以 2026-07 一条行宽 33 的记录为例：

```
位置[13] 表头名 K+                  实际值 'SF2'      ← 其实是 Vessel ID
位置[14] 表头名 Ca++                实际值 'R2606'    ← 其实是 Batch ID
位置[15] 表头名 Pre-Dilution        实际值 '016'      ← 其实是 Cell Type
```

此处左移 3 列，但到批号处已左移 8 列 → 中间**又省略了 5 列**。
**后果：短行中段的检测值（pH/PO2/Gluc/Lac…）无法从 CSV 自身判断属于哪个通道。**
只靠月度文件，这部分数据是**不可解析**的。

### 8.3 🟢 但短行能被逐次文件救回（99.4%）

按 `(时间戳)` 归一化后与逐次文件比对：

| | 行数 | 占比 |
|---|---|---|
| 完整行（41 列，可直接按列名解析） | 6894 | 89.5% |
| 短行（需逆向） | 810 | 10.5% |
| └ 其中**能在逐次文件中找到对应记录** | **805** | **99.4%** |
| └ 补不回来（2026-07，手动导出已停之后） | 5 | 0.6% |

> ### ⛔ 因此：**逐次文件不能弃用，必须永久保留**
> 这**推翻**了第 3 节"今后只有月度文件、逐次可弃用"的说法。
> 两套文件是**互补**关系，缺一不可：
> - 月度 → 独有 4 个试剂批号列（逐次完全没有）
> - 逐次 → 列对齐正常，是 810 条错位行**唯一**的检测值来源
>
> ETL 的正确做法：**以月度为主表，用逐次修补短行的中段数值。**

### 8.4 ⚠️ 表头列数本身也会变（比行宽问题更隐蔽）

不是所有文件表头都是 41 列：

| 月份 | 表头列数 | 数据行宽 |
|---|---|---|
| 2025-12 | **38** | 其中 610 行是 **41 列 —— 比表头还宽** |
| 2026-02 | **38** | 33 / 38 / 41 混合 |
| 其余 13 个月 | 41 | — |

**后果：拿"本文件表头"做列名映射，在这两个月会全错。**
→ ETL 必须用**固定的 41 列标准表头**做权威列定义，不能信任单个文件的表头行。

### 8.5 ⚠️ 日期格式在 2026-07-16 当天切换

同一个文件里混着两种格式，按日期分界，非随机：

| 格式 | 时间范围 | 行数 |
|---|---|---|
| `M/D/YYYY`（`7/1/2026  8:45:08`） | 2026-07-01 → 07-15 | 203 |
| `YYYY-M-D`（`2026-7-16  8:44:49`） | 2026-07-16 → 07-23 | 90 |

→ ETL 解析日期必须**两种格式都试**，只认一种会在 7/16 当天整体失败。
→ 需查明是谁在 7/16 改了仪器 PC 的区域设置（**待办**）。

### 8.6 🟢 附带好消息：7/16 起短行消失了

2026-07-16 之后的 90 行**全部是 41 列**，没有一条短行。
与日期格式切换是同一天 —— 疑似有人当天改了仪器导出/区域设置。
**若确认是导出设置改好了，"未测通道留空占位"这个治本待办可能已经解决**，
但需要向操作员确认改了什么、并保证不被改回去（**待办**）。

### 8.7 结论：ETL 可以开工，但必须遵守

1. 用**固定 41 列标准表头**做列定义，不信任文件自带表头（§8.4）
2. 完整行（41 列）按列名映射；短行**从末尾锚定**取批号和时间（§8.1）
3. 短行中段数值**从逐次文件补**，补不到的置空并标记，**不许猜**（§8.2 / §8.3）
4. 日期两种格式都要能解析（§8.5）
5. **逐次文件永久保留**，它是 810 条记录的唯一数据源（§8.3）

## 9. 根因确认：只有血气通道被禁用过（2026-07-23）

> 负责人提出假设：**血气校准不通过时，操作员会禁用相应通道**，导致导出缺列。
> 实测证据支持这个假设，且指向性非常干净。

### 9.1 直接证据：逐次文件表头缺的列，永远只有那三个

逐次导出文件的**表头会跟着少列**（通道被禁用时表头也不写），所以它直接记录了「当时禁用了谁」。
311 个逐次文件统计：

| 文件数 | 表头缺的列 |
|---|---|
| 289 | （不缺，完整） |
| 14 | `PCO2` |
| 5 | `PCO2` + `PO2` + `pH` |
| 3 | `PO2` |

**只有 pH / PO2 / PCO2 这三个血气通道出现过，生化通道（Gln、Glu、Gluc、Lac、NH4+、Na+、K+、Ca++）
一次都没有被禁用过。** 分布在 2025-09 → 2026-07 的 10 个月里，是长期、反复发生的操作。

### 9.2 旁证：月度短行解码出的省略组合也全是血气

对 805 条有逐次对照的短行做约束解码，成功解释 359 条，**省略集合无一例外落在血气组内**：

| 行数 | 省略的列 |
|---|---|
| 216 | `pH`, `pH @ Temp`, `PO2 @ Temp` |
| 62 | `PCO2`, `PCO2 @ Temp`, `CO2 Saturation` |
| 53 | `PO2`, `PO2 @ Temp`, `O2 Saturation` |
| 16 | `pH`, `PO2` |
| 12 | `pH`, `PO2`, `pH @ Temp`, `PO2 @ Temp`, `PCO2 @ Temp`, `O2 Saturation` |

规律：**禁用一个实测通道，会连带省略它派生的量**（@Temp、饱和度、HCO3）。
所以一次禁用通常少 2–3 列，三个通道全禁则少 6–8 列 —— 正好对应实测的 39/38/35/33 四种行宽。

> 其余 446 条未能自动解释，原因是逐次文件自身在这些记录上也有异常（见 §9.3），
> 属**比对方法受限**，不是反证。人工核对其中一条（2025-09-24 A1-D6）确认是 `PCO2` 被禁用，与假设一致。

### 9.3 ⚠️ 新发现：通道被禁用时，逐次文件的派生列也可能错位

以 2025-09-24 A1-D6 为例（`PCO2` 已禁用）：

```
pH=7.009  PO2=57.2  |  pH@Temp=7.009  PCO2@Temp=57.2  PO2@Temp=38.4
```

`PCO2@Temp` 的值与 `PO2` **完全相等**，且连续 9 条禁用 PCO2 的记录都如此。
正常文件里 `PCO2@Temp ≈ 0.84 × PCO2`，从不等于 `PO2`。

→ **说明「省略不留空」的问题在逐次文件里同样存在**，只是因为表头也跟着少列而被部分掩盖。
→ 修正 §8.3 的说法：逐次文件对**生化通道和原始测值**是可靠的补救源（这部分实测完全对得上），
   但这些记录里**血气的派生量（@Temp / 饱和度 / HCO3）需人工复核后才可入库，不可直接采信**。

### 9.4 对 SOP 和 ETL 的含义

1. **根因是「血气校准不过 → 禁用通道」，不是随机故障。** SOP 应针对这个场景写，
   而不是笼统写"不许禁用通道"——校准不过时操作员往往别无选择。
   建议改为：**原则上不禁用；确需禁用必须报备，并当场单独导出该样品。**
2. **受影响的只有血气结果，生化结果（糖、乳酸、离子等）从未被禁用**，
   趋势分析的主力指标不受损失——但前提是解析时正确处理左移，否则**位置全错**。
3. 行宽不能反推省略了谁（同为 38 列有多种组合），**必须靠逐次文件或报备记录**。

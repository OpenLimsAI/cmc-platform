## 1. 缘起

从「这个 Alembic migration 怎么用」起步，排查中发现 Mac 本地早已做过一次**大规模重新架构**，
而 `cmc-schema-migrations` 仓库和 Linux 部署都还停在旧世界，三者已严重脱节：

- 仓库假设 `cmc_data_platform` 在 Docker 容器 `postgres16:5432`、停在 Alembic `003`、含 4 个 schema。
- Mac 实际：项目从 `~/Python/...` 迁到 `~/code/...`（旧 venv 失效）；`postgres16` 容器删除，
  `cmc_data_platform` 迁入 `rd_pg` 容器；并把单库**拆成多库**（cmc_rd / cmc_analytics / cmc_gmp / cmab_mdm），
  `meta` / `raw_qc_lims` 等已拆走；新库上无 `alembic_version`。
- Linux 实际：仍是**单库** `cmc_data_platform`（8 schema），5 个应用共用，停在 `003`。

## 2. 关键决策（用户确认）

| # | 决策 |
|---|---|
| D1 | `rd_pg` 里的库为新真理来源；`meta`/`raw_qc_lims` 系有意拆走 |
| D2 | 不再追求「单库两端完全一致」——架构已演进为多库；仓库职责相应调整 |
| D3 | Linux 与 Mac 对齐采用**推平重建（nuke & pave）**，而非逐表迁移 |
| D4 | 业务/ETL 数据**全部丢弃重来**（material_mgmt 库存、raw_* 等）；cost_accounting/cmab_mdm 只建表暂不导数据；ETL 库靠重跑 |
| D5 | Linux 用 **3 个原生 PG 集群**（不用 Docker），端口 5432/5433/5434，对齐白皮书 |
| D6 | 角色密码用 **Mac 同名角色的 SCRAM 哈希**，两端完全一致、同一套 `.env` 通用 |

## 5.2 Alembic 多库统一 + 重做 baseline（2026-06-04）

把 schema 变更统一成「每库一套 alembic、改任何库流程不变」：

- 本仓库 `cmc-schema-migrations` 改为**多环境 alembic**（一个 `alembic/env.py`，按 `alembic -n <库名>` 选库），
  管 **cmc_rd / cmc_analytics / cmc_data_platform / cmc_gmp** 四个无 ORM 的共享库。
- 每库用 `pg_dump --schema-only` 生成**单个干净 baseline**（`alembic/baselines/<库>.sql`，可从空库重建），
  旧 001–004 归档至 `alembic/versions/_legacy/`。Mac + Linux 两端均 `stamp <库>_baseline`（cmc_data_platform 用 `--purge` 清旧 004）。
- **cmab_mdm 保持其 app（cmab-mdm-platform）自带 alembic**（autogenerate，现 head=0040），不并入。
- 连接：`.env` 用共享凭据（`PG_USER`/`PG_PASSWORD` + 端口按库），Mac/Linux 端口相同故两端通用。
  Linux 两集群 postgres 密码、Mac gmp_pg 的 postgres 密码均统一为同一值。
- 统一入口 `./dbmig`：`dbmig list` / `dbmig <库> <alembic 子命令>`（cmab_mdm 自动转发到 app）。

**日常流程（任何库一致）**：Mac 改 schema → `dbmig <库> revision -m "…"` → 编辑 → `dbmig <库> upgrade head`（Mac 测试）→ push；Linux `git pull` → `dbmig <库> upgrade head`。

> ⚠️ 遗留：本仓库目前**不是 git 仓库**（靠 scp 同步）。要让「push/pull」真正成立，需 git init + GitHub 远端（见报告中的后续建议）。

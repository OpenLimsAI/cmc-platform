# 统一筛选级联修正

> 日期：2026-10-09｜状态：负责人已授权按方案继续 push/Linux 部署；代码已实现、验证进行中，尚未发布本次修正。+
## 来源与已核实问题

负责人发现选择“注射用水”后，水点号及其他下拉仍展示全量候选。已核对当前代码：结果查询应用 FilterSpec，但 GET `/api/v1/filters` 只应用固定水样范围，前端也以不含筛选条件的缓存键读取候选；目前只有水点号变化会清空内部点位 ID。这与统一筛选的用户场景不一致。

## 已确认规则

1. 按界面顺序向下联动：水类型 → 水点号 → 水点（编号/名称/内部 ID）→ 检项 → 方法 → 版本 → 阶段 → 参数 → 单位。无需按顺序逐项选择；未选上游条件不限制下游。
2. 某下拉的候选应用日期、样品状态、固定授权数据范围及它前面的已选条件；不应用自身或后面的条件，避免已选值把自己锁死。日期使用既有 Asia/Shanghai 包含起止日规则，版本和单位仍独立匹配。
3. 改变或清除上游条件时，清空其后的已选条件；改变日期/样品状态时，保留水类型，清空水点号及后面的条件。比较组、追溯、分页和已生成的下载沿用现有失效规则。
4. 同号不同 LIMS 内部 ID 不合并。编号/名称候选来自既有 staging 主表映射，不根据 WFI/PW 前缀推断水类型。无对应结果的选项不展示；无结果、加载中和查询失败分别提示。
5. 切换条件后立即读取新候选，缓存键包含完整筛选与身份；旧响应不能覆盖新条件。URL 深链与浏览器前进/后退恢复相同筛选并重新读取候选。

## 接口与影响

GET `/api/v1/filters` 接受与结果查询相同的 FilterSpec 查询参数（补全文档中的 samplepoint_code），复用后端校验、只读事务及数据范围；返回现有 options/point_options 结构，增加实际使用的 filter 字段。一次响应内的候选和上下文来自同一只读事务。

修改限于看板后端、前端及 docs/02、07、09、10。本次不涉及数据库结构、ETL、点位主数据写入、Hub 路由、端口或人员授权。

## 验收计划

- 用独立测试数据核对不同水类型、同号不同内部 ID、检项/方法/版本/参数/单位，日期包含边界与状态均参与候选查询。
- 核对自己的选择及下游条件不会限制上游候选；无结果、无效筛选、查询失败与未授权仍有正确反馈。
- 前端验证改变/清除上游后重置下游，日期/状态变化以及 URL 恢复、快速切换不会展示旧候选。
